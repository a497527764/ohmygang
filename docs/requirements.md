# 心之钢群聊 — 需求分析

> 版本：第一版（MVP）· 修订版（2026-11-02 设计审查后）  
> 平台：Windows 桌面常驻  
> 网络：去中心化（局域网 UDP → 加密公共中继；打洞直连移到第一版之后）  
> 技术倾向：Rust 核心 + TypeScript 桌面 UI（Tauri）  
> 交付物范围：本文仅需求；实现代码不在本次范围  
> 相关文档：`architecture.md` · `module-interfaces.md`

---

## 1. 产品概述

### 1.1 一句话描述

Windows 桌面常驻的去中心化群聊客户端：通过房间码创建/加入房间，主界面以聊天为主；同一用户在短时间窗口内连发消息可触发「心之钢」叠层与音效；每个群具备类似微信的群管理页，含心之钢排行榜，成员头像右下角展示层数角标。支持多群切换，以及聊天记录与层数的本地持久化。不自建业务服务器。

### 1.2 目标用户

小规模朋友群（开黑、同学、同事等），核心动机是玩梗、互动与留存，而非企业级即时通讯。

### 1.3 设计原则

- **聊天为主，玩梗为钩子**：主界面始终是会话；心之钢是增强，不是独立游戏屏。
- **玩法先行**：先验证「连发叠层」好不好玩，基础设施按阶段推进（见 2.4）。
- **无自建服务器**：跨网转发借用公共中继，也允许用户填写自己的中继地址；内容端到端加密。
- **可反复打开**：多群、历史、层数在本地保留，关掉重开仍可用。
- **对等可用性**：无云端消息仓库；历史依赖「持有日志的对等节点在线并可同步」。
- **防君子**：心之钢是朋友间的玩梗。防止误操作和普通客户端的重复计数，不防专门改过的客户端（见 4.3）。

## 2. 目标与成功标准

### 2.1 第一版必须具备（P0）

| 编号 | 能力 |
|------|------|
| P0-1 | 创建房间 / 房间码加入；仅需昵称，无中心登录账号 |
| P0-2 | 实时文字聊天（主界面）；消息最终送达：去重、自动重发、对等补齐 |
| P0-3 | 心之钢规则：同一人在 **5 秒**内发送满 **3** 条消息则叠 1 层；个人冷却 **30 秒**；**房间级**规则可配置（见 3.4） |
| P0-4 | 触发时播放内置的心之钢音效；**本机**总开关/音量 |
| P0-5 | 成员头像右下角显示心之钢层数；群管理页含心之钢排行榜（布局参考微信群资料/管理页） |
| P0-6 | 多群：本地保存多个房间，可切换当前活跃房间 |
| P0-7 | 持久化：按房间保存聊天记录与每人心之钢层数；提供身份备份功能和可选的房间事件备份 |
| P0-8 | 网络：**局域网 UDP → 加密公共中继**；中继列表内置默认值并可由用户修改 |
| P0-9 | 平台：Windows 优先交付 |

### 2.2 明确非目标（第一版不做）

- 自建业务服务器、中心账号体系、陌生人广场/推荐
- 音视频通话、大文件传输专项、已读回执等企业 IM 能力
- macOS / Linux 客户端交付（架构可预留）
- 「谁在摸鱼」状态看板（可作为后续版本）
- **打洞直连、好友系统、私聊房、自定义头像图片**（均为 P1，见 3.7）
- **防作弊**：不防改过的客户端伪造时间戳或触发消息来刷层数
- **同一身份多台设备同时在线**
- **云端永久消息存储**；全员离线期间仍可从「云」拉取历史
- **密码学意义上的踢人**（持有房间码者仍可重入；安全操作是新建房间）

### 2.3 成功标准（验收）

1. 多名用户分别安装后：一人建房并分享房间码，其余人可加入；房间码输错时被校验位拦下并提示。
2. 同网与跨网场景下均能完成进房与聊天（跨网经加密公共中继）；跨网验收在目标用户的真实网络上进行。
3. 按**房间规则**触发心之钢：仅作者端发出叠层事件；全员层数一致，包括后加入的成员，也包括事件乱序到达的情况；本机可播音效。
4. 退出并重启应用后，对应房间的聊天记录与层数仍在。
5. 用户可维护多个房间并切换。
6. 人为丢包/断网重连后，未确认消息自动补发；重复投递不产生重复气泡或重复叠层。
7. 断线重连后一次补齐大量历史叠层事件时，层数正确更新，且不连续播放音效。
8. 恢复身份备份后，同步回来的本人旧消息不会产生新的叠层。

### 2.4 分阶段交付

| 阶段 | 范围 | 完成标志 |
|------|------|----------|
| 开工前 | 在中国大陆、不开代理的直连网络上实测公共中继，至少覆盖两个运营商（工具在本地 `tools/relay-probe`，不入库） | 得到符合 4.1「国内直连」的默认中继列表；若全部不通，先回来决策 |
| M1 玩法闭环 | 建房/进房、局域网与中继、实时聊天、状态事件同步、心之钢判定与重放、音效、角标与排行榜、SQLite 持久化 | 同网和跨网各两台机器连发能叠层，层数一致，重启后还在（2026-11-03 完成；移动/联通网络上逐个中继的测试结果待补记） |
| M2 可靠与同步 | 聊天补齐、投递状态与自动重发、断线恢复、多房间切换、身份与房间备份 | 验收 5、6、7、8（2026-11-03 完成，均有自动测试和单机双开自测） |
| M3 交付 | 群管理页完善、托盘常驻、Windows 安装包 | 全部验收（2026-11-03 完成开发和单机自测，对照见 [acceptance.md](acceptance.md)；两台机器用安装包复验由所有者进行） |

> 2026-11-02：开工前实测只覆盖了四川电信（3 个网络），所有者决定先开工 M1。移动、联通的补测并入 M1 的跨网验收。

## 3. 功能需求

### 3.1 身份与昵称

- 首次启动生成本地密钥对；`memberId` 就是公钥，不可伪造。
- 用户可设置全局显示昵称（各房间相同）；昵称允许重名，**信任以公钥指纹为准**。
- 头像第一版按公钥和昵称自动生成（颜色 + 昵称首字），自定义图片为 P1。
- 昵称变更通过 `Profile` 事件同步到本人所在的全部房间（不只是当前活跃房）。
- 无中心登录；换机通过备份文件导入。备份文件必须设置口令。
- 同一身份同一时间只在一台设备上使用。恢复备份后，房间先进入「加入中」，与至少一名成员同步后才能发言。

### 3.2 房间

- **创建房间**：生成房间码（含 128 位随机密钥、房主公钥摘要和校验位，约 48 个字符，以复制粘贴为主）；可设置群名称；创建者成为**房主**。房主身份由房间码绑定，其他持码者无法冒充；第一版不支持转让。
- **加入房间**：粘贴或输入房间码，校验位不对时立即提示。进入「加入中」状态，与任一在线成员同步后才能发言；无人在线时界面说明原因并持续等待，可取消。
- **成员列表**：昵称、头像、指纹摘要、心之钢层数、传输路径提示等。
- **退出房间**：本地可保留历史只读回看；层数保留，重新进房后恢复；排行榜只列当前成员。
- **解散房间**：仅房主，不可撤销。离线成员下次遇到知情成员时才知道。解散时间之后产生的叠层无效、消息不显示；本地历史可只读保留。
- **房主丢失密钥**：房间仍可聊天，但无法再改规则、改名或解散。
- **多房间**：列表与切换；非活跃房降低同步频率，但仍接收消息。
- **威胁模型（房间码）**：房间码 ≈ 入场券 + 对称密钥材料。码泄露则持有者可解密该密钥下的密文并重入。MVP **不提供**对「仍持有旧码者」的强制剔除。
- **换码**：第一版的做法是新建房间，把新码发给想保留的人；历史和层数不迁移。
- **新成员可见历史（MVP）**：成员、房主、规则、层数等状态完整同步；聊天记录默认同步最近 N 条（局域网 N=5000，中继 N=500，可配置）；更早的聊天尽力而为，不承诺。

### 3.3 聊天

- 文本消息：内容、发送者、时间、`eventId`。单条文本上限 900 字节（约 300 个汉字）。
- 主界面会话流；输入框发送；成员加入、退出、改群名等以系统提示显示在会话中。
- **消息最终送达（P0）**：发送后立即写入本地日志，显示「发送中」；至少一名其他成员确认持有后显示「已发送」。没有「发送失败」状态：只要消息未被确认，就继续自动重发，并在遇到任何成员时补齐，用户无需手动重发。收端按 `eventId` 去重。
- **排序**：按作者时间显示。对方时钟偏差超过 2 分钟时，按本机收到时间显示并提示。排序只影响显示，不影响层数，也不要求各成员完全一致。
- 本地持久化；与持有更全日志的同伴连通时可补齐缺失事件。

### 3.4 心之钢

- **房间级规则**（默认：窗口 5s、阈值 3 条、冷却 30s）：写入房间创建事件，变更须经房主发出的 `ConfigNotice`；所有历史规则版本都保留。取值范围：窗口 1–60 秒，阈值 2–10 条，冷却 1 秒–1 小时。
- **本机偏好**：音效开关、音量（不影响层数一致性）。
- **触发**（只在本人发送消息时判定，仅作者客户端生成 `heartsteel` 事件，其它端不得本地发明叠层）：
  - 只统计冷却结束之后发出的本人消息；冷却期内发的消息不计入下一次窗口。
  - 取最近「阈值」条，首尾时间差 ≤ 窗口（含边界）即触发。
  - 冷却从触发消息中最后一条的时间算起，到「该时间 + 冷却时长」结束（含边界）。
  - 例：第 0、1、2 秒发 3 条，触发，冷却到第 32 秒。第 28、29 秒发的不计入；接着第 32.5、33、34 秒发 3 条，再次触发。
- **层数**：等于该成员有效叠层事件的条数，由重放得出。同一批事件无论到达顺序如何，算出的层数都相同。
- **音效**：只对实时收到或本机产生的有效叠层事件播放；补齐回来的历史叠层只更新层数，不播放。受本机静音、音量和房间免打扰约束。
- **防重复**：同一条消息不能触发两次；恢复备份后同步回来的旧消息不触发。
- **排行与角标**：与重放得到的层数一致。

### 3.5 群管理页（UI 参考微信群资料）

- 群名称、成员搜索与成员网格、添加成员入口（复制房间码）。
- 群公告等：第一版可最小占位；**必须含心之钢排行榜**。
- 排行榜按层数降序，与角标一致。
- 免打扰、置顶等：本机偏好即可。
- **未读数**：按该房间「本机尚未标记已读的聊天事件条数」计数，迟到的旧消息也算；切到活跃房并浏览会话视为已读（MVP 不做已读回执同步到他人）。首次进房同步的历史不计入未读。

### 3.6 系统配置

- **房间规则**（房主）：心之钢窗口/条数/冷却。
- **本机**：音效开关与音量、是否允许互联网/中继、中继列表、LAN 提示、身份/数据备份、历史同步上限 N（只影响聊天记录，不影响层数）。

### 3.7 第一版之后（P1）

设计要点保留在 `architecture.md` 第 12 节，第一版不实现：

- **打洞直连**：中继已能兜底跨网，打洞主要降低延迟和中继流量。
- **好友系统**：好友码、好友列表、在线邀请、离线收件箱。
- **私聊房**：依赖好友系统。
- **自定义头像图片**：需要分片传输。

## 4. 网络与安全需求

### 4.1 拓扑

1. **数据路径（按序）**：局域网 UDP → 加密公共中继。
2. **公共中继**：只转发密文；采用 Nostr 临时事件；**不得**当作历史数据库。内置默认列表，用户可增删，也可填写自己的中继。
3. **虚拟局域网**（ZeroTier 等）：网络内广播可达时视为类局域网路径。
4. **跨网前提**：跨网至少需要一个双方都能连上的中继。
5. **国内直连**：默认中继必须在中国大陆不开代理时直连可用，并达到 lolPing 的标准：连接不超过 5 秒；回显中位数不超过 1 秒、p95 不超过 2 秒；5 条/秒持续 30 秒不被限流且回显不低于 99%；断线后能重连。只在开代理时才能连上的中继不算（damus、nos.lol 等知名中继在国内直连被封）。

### 4.2 历史可用性（显式约束）

- 无云端消息仓库。
- 同步模型为 **对等相遇补齐**（peer catch-up）。任何持有事件的成员都可以提供补齐，不必等原作者上线。
- 当房间内无人在线且本地无数据时，新设备**不能**凭空拉取云历史。
- 中继上的临时事件没有存储保证，对方不在线时不会被转交；持久化只信任本地 `events` 日志及从对等节点同步的结果。

### 4.3 加密、隐私与威胁模型

- 房间对称密钥由房间码派生；消息与心之钢事件 E2E；作者身份密钥签名。
- 中继可见：IP、匿名房间标识、时间等元数据；不可读明文，也无法把同一个人在不同房间的活动通过密钥关联起来。
- 私钥和房间码在本机加密保存；聊天记录第一版不加密落盘（不防能直接访问本机文件的人）。

| 防得住 | 防不住（已接受） |
|--------|------------------|
| 中继和网络窃听者读取内容 | 持有房间码的人读取内容、进入房间 |
| 持码者冒充其他成员发言 | 持码者灌水（只做速率和大小限制） |
| 持码者冒充房主 | 改过的客户端伪造时间戳或触发消息来刷层数 |
| 普通客户端的重复叠层、乱序导致的层数不一致 | 恶意作者用同一序号发不同内容（只检测和提示） |

### 4.4 规模与中继预算

- 单房软上限约 16–32 人。
- 中继是免费公共设施，发送遵守预算：单客户端约 5 条/秒、突发 10 条（来自 lolPing 的实测）。
- 每房本地默认保留全部事件；N 只限制给新成员同步多少聊天记录。

## 5. 数据持久化需求

- 本地存储：身份密钥（加密）、房间元数据与房主信息、房间码（加密）、每房间事件日志、成员层数缓存、UI/本机偏好、全部房间规则版本。
- 备份：身份备份必须设口令；房间事件包可选，以便换机后减少对「同伴在线补齐」的依赖。

## 6. 约束、假设与风险

### 6.1 约束

- 不运营自建业务服务器。
- 第一版只交付 Windows。
- Rust 核心 + TypeScript UI。
- 安装包内置心之钢音效（2026-11-02 所有者决定）。音效和应用图标都是第三方游戏素材，只限群友私下使用，公开发布前需要替换。

### 6.2 假设

- 房间码主要通过线下或其他通讯工具传播。
- 用户愿意授予局域网权限；跨网时允许公共中继。
- 用户理解去中心聊天的历史可用性限制（可在 UI 用一句话说明）。
- 用户接受层数只防君子。

### 6.3 风险与对策

| 风险 | 对策 |
|------|------|
| 公共中继在国内直连不可达 | 开工前在多个运营商的直连网络实测；中继列表可配置，必要时填自己的中继 |
| 公共中继不稳定或限流 | 多中继同发；按回显判断健康；遵守发送预算 |
| 丢包导致聊天缺口 | 自动重发 + 对等补齐 + eventId 去重 |
| 层数不一致 | 状态事件永不裁剪；验签后入库，有效性在重放时计算 |
| 昵称冒充 | 指纹为准；UI 展示指纹摘要入口 |
| 房间码泄露 | 威胁模型公示；新建房间 |
| 换设备丢数据 | 身份备份 + 可选房间备份 |
| 配置不一致导致不公正叠层 | 房间级规则 + ConfigNotice + 规则版本历史 |
| 中继补齐较慢 | 中继默认只补 500 条聊天；局域网可补 5000 条 |
