# 心之钢群聊 — 架构设计

> 版本：第一版（MVP）· 修订版（2026-11-02 设计审查后）  
> 对应需求：[requirements.md](./requirements.md)  
> 网络路线：局域网 UDP → 加密公共中继；打洞直连移到第一版之后  
> 桌面壳：Tauri 2（Rust 核心 + TypeScript UI）  
> 范围：仅架构设计，不含实现代码

---

## 1. 目标与约束回顾

- Windows 桌面常驻；无自建业务服务器。
- 房间码建/进房；多群；本地持久化。
- 心之钢：默认 5s / 3 条 / 冷却 30s；**房间级规则**；**仅作者客户端生成叠层事件**；本机音效偏好。
- 跨网走加密公共中继；不承诺云端历史。
- 一致性目标：所有诚实客户端拿到同一批事件后，算出相同的房主、成员、规则和层数。

## 2. 总体架构

### 2.1 进程与技术分层

```
┌─────────────────────────────────────────┐
│  TypeScript UI (Tauri WebView)          │
│  聊天 / 群管理 / 设置 / 托盘             │
└──────────────▲──────────────────────────┘
               │ Commands + Events
┌──────────────┴──────────────────────────┐
│  Rust Core (async runtime)              │
│  core · identity · rooms · chat         │
│  sync · heartsteel                      │
│  protocol · transport · crypto · storage│
└──────────────▲──────────────────────────┘
               │
          LAN UDP / Public Relay
```

- **UI**：展示与输入；不实现传输、去重判定、叠层判定。
- **Rust 核心**：身份、房间状态、加解密、传输、同步、心之钢、SQLite、事件总线。
- **无用户部署的业务服**；公共中继为第三方基础设施。

### 2.2 逻辑模块

| 模块 | 职责 |
|------|------|
| `core` | 进程入口；入站事件分发；把各模块产生的新事件交给 `sync` 发送；向 UI 发事件 |
| `identity` | 密钥、memberId、昵称、备份 |
| `rooms` | 建房/进房/多房、由状态事件推导房主、成员、规则、解散 |
| `chat` | 发送、消息列表、显示顺序、未读 |
| `sync` | 首发与重发、Have/Want 补齐、新成员同步（合并了原 `reliability`） |
| `heartsteel` | 作者端判定、重放算层数、排行榜 |
| `protocol` | 事件与帧的编码、`event_id` 计算、无状态校验、封包/解包 |
| `transport` | 局域网 UDP 与中继；只收发不透明字节 |
| `crypto` | KDF、AEAD、签名 |
| `storage` | SQLite |
| `settings` | 本机偏好读写（音效开关与音量、网络、中继列表等） |
| `ui`（TS） | 页面与订阅 |

### 2.3 与 lolPing 的异同

- **同**：房间码、局域网优先、跨网公共中继密文、无自建业务服、E2E。以下做法直接沿用：包不超过 1200 字节、公钥决定成员 ID、频繁更换 Nostr 密钥、房间码校验位、按回显判断中继健康、发送限速和洪水防护。
- **异**：lolPing 是发完即忘（历史退出即清空）。本项目新增持久群聊、签名事件日志、对等同步和心之钢。lolPing 的房间码约 45 位熵，配合 scrypt；本项目的密文对应长期保留的历史，改用 128 位随机密钥。

## 3. 房间码与密钥

```text
room_secret = 16 字节随机数
owner_tag   = SHA-256(房主公钥) 前 10 字节
payload     = room_secret ‖ owner_tag                      # 26 字节
check       = SHA-256("hs/code/v1" ‖ payload) 前 10 位
房间码      = "HS1-" + Crockford Base32(payload ‖ check)    # 共 48 个字符
```

"HS1-" 之后是 44 个 Base32 字符（218 位，末尾补 2 个 0 位）。展示时每 4 个字符一组，解析时忽略连字符、空白和大小写。校验位不对立即报错，否则打错的码会算出一把「有效」密钥，用户会进入一个永远没人的空房间。10 位校验位约有 1/1024 的概率漏过一个抄错的码。

```text
prk      = HKDF-Extract(salt = owner_tag, ikm = room_secret)
room_key = HKDF-Expand(prk, "hs/room-key/v1", 32)
room_id  = HKDF-Expand(prk, "hs/room-id/v1", 16)
```

- `room_secret` 已是 128 位随机数，不需要 scrypt 这类慢速 KDF（慢速 KDF 用来保护低熵口令）。
- `owner_tag` 参与派生。把别人的公钥摘要换进房间码，只会得到另一个房间，无法劫持原房间。
- `room_id` 由密钥派生，看不出房间内容，同时用作局域网包头和中继主题。
- 包加密用 XChaCha20-Poly1305，24 字节随机 nonce，多人共用一把密钥也不必担心 nonce 碰撞。

**房主的信任根**：`RoomCreate` 事件的作者公钥满足 `SHA-256(公钥)[..10] == owner_tag` 才算房主。伪造需要找到 80 位的第二原像，不可行。

**换码**：第一版等于新建房间，不是原地改码；历史和层数不迁移。

## 4. 事件模型

### 4.1 结构

```text
UnsignedEvent {
  format: u8            # 事件格式版本，当前为 1
  room_id: [u8; 16]
  author_id: [u8; 32]   # Ed25519 公钥，同时就是 memberId
  stream: u8            # 0 = state（永不裁剪），1 = chat（可按 N 限制同步）
  seq: u64              # 同一作者、同一 stream 内从 1 连续递增
  ts_ms: u64            # 作者本机时间，同一作者严格递增
  kind: u16             # 事件类型
  body: bytes           # 作者编码一次的 CBOR，收端原样存储
}
event_id = SHA-256("hs/event/v1" ‖ 以上字段按序定长拼接 ‖ body 长度(4 字节) ‖ body)
sig      = Ed25519(作者私钥, "hs/sig/v1" ‖ event_id)
```

- `memberId` 就是公钥，验签不需要查表，也不依赖 `Join` 事件是否已同步。指纹摘要取 `SHA-256(公钥)` 前 8 字节的 Base32。
- `event_id` 由内容决定，同一 ID 不可能对应两份内容。
- `body` 只编码一次、按原始字节算哈希，收端不重新序列化，因此不存在规范化编码问题。
- `ts_ms = max(本机时间, 本人上一事件 ts_ms + 1)`，保证同一作者严格递增，时钟回拨也不影响。
- 定长拼接全部用大端：format 1 字节、room_id 16、author_id 32、stream 1、seq 8、ts_ms 8、kind 2，然后是 body 长度（u32，4 字节）和 body。

### 4.2 类型

| stream | kind | body | 说明 |
|--------|------|------|------|
| state | `RoomCreate` | title, rule | 作者须匹配 `owner_tag` |
| state | `Join` / `Leave` | 空 | 进出房间 |
| state | `Profile` | nickname | 昵称，上限 32 字符 |
| state | `Rename` | title | 仅房主，上限 64 字符 |
| state | `ConfigNotice` | rule | 仅房主 |
| state | `Dissolve` | 空 | 仅房主，不可撤销 |
| state | `Heartsteel` | rule_epoch, triggers | 见第 5 节 |
| chat | `Chat` | text | 上限 900 字节 |

**kind 编号**：RoomCreate 1、Join 2、Leave 3、Profile 4、Rename 5、ConfigNotice 6、Dissolve 7、Heartsteel 8、Chat 100。body 用 CBOR 编码，事件 ID 等字节字段编成 CBOR 字节串。

**未知 kind**：签名有效就入库并可转发给别人，但不显示、不参与计算。否则旧版本客户端会把它一直当作缺失反复拉取。

### 4.3 入库规则

收到事件时**只做无状态校验**，结果不依赖本机已有什么，因此不会造成成员间分歧：

1. `format` 受支持，body 不超过 1024 字节；
2. `event_id` 与内容相符，`sig` 验证通过；
3. `room_id` 与当前房间一致；
4. 状态事件 `seq ≤ 100000`（诚实用户达不到，防止灌爆状态日志）。

通过就入库；**是否有效放到重放时计算**。触发消息不在、规则还没到、事件乱序到达，都不会导致丢弃。这样同一批事件在任何到达顺序下结果都相同，被丢弃的事件也不会在同步时被反复拉取。

### 4.4 分叉

同一作者、同一 stream、同一 `seq` 出现不同 `event_id`，称为分叉。来源是恶意客户端，或违反单设备约定。

- 两条都入库，UI 标记该成员异常。
- 状态事件重放时，同序号只取 `event_id` 字典序最小的一条。
- 聊天事件按 `event_id` 去重，两条都显示。
- 不保证所有成员都能拿到两条，这属于第 11.3 节已接受的风险。

### 4.5 显示顺序与未读

显示顺序是本机视图，不要求全员一致，也不参与层数计算。入库时计算并存储 `display_ts`：

| 情况 | `display_ts` |
|------|--------------|
| 实时帧收到，且 `ts_ms` 与本机时间相差超过 2 分钟 | 本机时间，并提示对方时钟偏差 |
| 补齐帧收到，且 `ts_ms > 本机时间 + 2 分钟` | 本机时间 |
| 其他 | `ts_ms` |

- 消息列表按 `(display_ts, event_id)` 排序，分页游标也用这对值。
- 每条事件入库时分配本机递增的 `local_seq`。已读游标记录 `local_seq`，所以 `ts` 很旧的迟到消息也算未读。
- 首次进房同步完成时，已读游标移到当前最大值，历史不计入未读。

## 5. 心之钢

### 5.1 规则

```text
Rule { rule_epoch: u32, window_ms: u32, threshold: u32, cooldown_ms: u32 }
默认：epoch 0，5000 / 3 / 30000
范围：window_ms 1000..=60000，threshold 2..=10，cooldown_ms 1000..=3600000
```

- epoch 0 写在 `RoomCreate`；之后每条 `ConfigNotice` 的 epoch 必须大于同一房主之前的所有 epoch。
- `rule_epoch` 由核心分配，不由 UI 传入。
- 所有版本都保留在 `room_rules` 表，否则校验不了历史事件。
- 超出范围的规则无效。

### 5.2 事件内容

```text
HeartsteelBody { rule_epoch: u32, triggers: Vec<(EventId, ts_ms)> }
```

事件自带触发消息的 ID 和时间，校验不依赖聊天原文，聊天被裁剪或还没到都不影响层数。原设计的 `stacks_after` 和 `cooldown_ms` 已删除：作者可随意填写，且都能从规则和日志算出。

### 5.3 作者端触发

**只在本人调用 `send_text` 时判定**，和聊天事件写入放在同一个数据库事务。同步回来的本人旧消息不经过这条路径，所以恢复备份不会重复叠层；崩溃也不会丢失已满足的触发。

```text
fn evaluate_emit(my_chats, last_valid, rules, current_rule, new_msg) -> Option<triggers>:
    cooldown_end = 无 last_valid ? 0
                   : last_valid.triggers.last.ts + rules[last_valid.rule_epoch].cooldown_ms
    eligible = my_chats（含 new_msg）中 ts >= cooldown_end 的消息，按 ts 升序
    if eligible.len < current_rule.threshold: return None
    t = eligible 的最后 threshold 条
    if t.last.ts - t.first.ts <= current_rule.window_ms: return Some(t)
    return None
```

作者使用本机已知的最新规则。其他端只验证和重放，不生成叠层事件。

### 5.4 重放（层数的唯一来源）

每位作者独立计算，是事件集合的纯函数：

```text
fn replay_author(heartsteel_events, rules, dissolve_ts) -> 有效事件列表:
    按 (seq, event_id) 升序遍历；同一 seq 只取第一条
    last = None；used = {}
    对每个事件 h，t = h.triggers：
        r = rules[h.rule_epoch]；不存在 → 跳过（规则到达后重算）
        t.len != r.threshold → 无效
        t 的 ts 不是严格递增 → 无效
        t.last.ts - t.first.ts > r.window_ms → 无效
        last 存在且 t.first.ts < last.t.last.ts + rules[last.rule_epoch].cooldown_ms → 无效
        t 中任何 event_id 已在 used → 无效
        dissolve_ts 存在且 t.last.ts > dissolve_ts → 无效
        通过：加入结果；last = h；把 t 的 ID 加入 used
层数 = 有效事件条数
```

- 新的 `Heartsteel` 事件到达时，只重算该作者。
- 新的 `ConfigNotice` 或 `Dissolve` 到达时，重算全房。
- `members.stacks` 只是缓存，和事件入库放在同一事务里更新。
- **不比较 `rule_epoch` 与事件时间**：时间由作者提供，比较也防不住作弊，反而会误伤规则变更时的正常乱序。

### 5.5 测试向量

规则 5000 / 3 / 30000，时间单位为秒。以下向量已用脚本验证（`evaluate_emit` 与 `replay_author` 结果一致）。实现时先写成单元测试。

| 编号 | 本人发送时间 | 层数 | 触发消息 | 说明 |
|------|--------------|------|----------|------|
| V1 | 0, 1, 2 | 1 | 0, 1, 2 | 基本 |
| V2 | 0, 2.5, 5 | 1 | 0, 2.5, 5 | 窗口含边界 |
| V3 | 0, 2.5, 5.001 | 0 | — | 超窗口 1 毫秒 |
| V4 | 0, 1, 2, 3, 4, 5 | 1 | 0, 1, 2 | 冷却内继续发不叠 |
| V5 | 0, 1, 2, 28, 29, 32.5 | 1 | 0, 1, 2 | 冷却内的消息不计入 |
| V6 | 0, 1, 2, 28, 29, 32.5, 33, 34 | 2 | 0, 1, 2；32.5, 33, 34 | 冷却后重新攒满 |
| V7 | 0, 1, 2, 32, 33, 34 | 2 | 0, 1, 2；32, 33, 34 | 冷却结束时刻含边界 |
| V8 | 0, 10, 11, 12 | 1 | 10, 11, 12 | 滑动窗口 |
| V9 | 0, 3, 6, 9 | 0 | — | 太慢 |

| 编号 | 重放输入 | 层数 | 说明 |
|------|----------|------|------|
| R1 | 两个事件用同一批触发消息 | 1 | 不能复用 |
| R2 | 触发 [0,1,2] 后接 [10,11,12] | 1 | 第二个在冷却内 |

| R6 | R5 的规则到达后 | 1 | 重算后计入 |
| R7 | 第 50 秒解散，第二个触发在 100–102 秒 | 1 | 解散后无效 |

另有一条性质测试：随机打乱到达顺序，层数不变；诚实作者生成的事件，重放时全部有效（含中途改规则）。

### 5.6 音效

`live = 事件来自 live 帧，且 |本机时间 - 触发消息最后时间| ≤ 60 秒`。

- 只有 `live` 且有效的叠层事件才通知 UI 播放，本人产生的事件同样如此。
- 补齐回来的事件只更新层数。这样断线重连补到 200 个历史叠层，也不会连放 200 次。
- 房间免打扰时不播；非活跃房默认播放，受本机总开关约束。

## 6. 传输

### 6.1 包格式

```text
Packet = "HS"(2) ‖ proto(1) ‖ room_id(16) ‖ nonce(24) ‖ AEAD(Frame) (含 16 字节 tag)
```

- 整包不超过 **1200 字节**，包头 59 字节，留给帧 1141 字节；不做分片。
- 包头前 19 字节（`"HS"`、proto、room_id）作为 AEAD 的关联数据，改动任何一个字节都解密失败；nonce 直接参与解密。
- `proto` 与本机不同时不解析，并提示「有成员版本不同，请更新」。

### 6.2 帧

帧使用 CBOR 编码，未知帧类型直接忽略。

```text
Events { live: bool, events: Vec<SignedEvent> }     # 实时广播或补齐响应，一包可放多条
Have   { from: MemberId, period_s: u16, vector: Vec<HaveEntry> }   # 见 7.2，同时充当在线心跳和确认
Want   { to: 短 ID, ranges: Vec<(作者短 ID, stream, from_seq, to_seq)> }
WantFloors { to: 短 ID, n: u32 }                    # 新成员询问「最近 n 条聊天」的分界
Floors { vector: Vec<(作者短 ID, floor_seq)> }
```

**线上编码**：
- 事件在线上省掉两个可推导的字段：room_id 已在包头，event_id 由内容算出。收端用包头的 room_id 补上、重算 event_id 再验签，每条事件少 48 字节。事件编码成 CBOR 数组 `[作者公钥, stream, seq, ts_ms, kind, body, sig]`。
- 帧是 CBOR 编码的枚举，变体名用一两个字母（`E` = Events、`H` = Have、`W` = Want，M2 再加 `WF`、`F`）；解不出来的帧直接忽略。
- 一个 Events 帧放不下时拆成多个包；Have 放不下时拆成多帧。

短 ID 是公钥前 8 字节。控制帧（Have、Want、Floors）不单独签名：能解密的都是持码者，伪造它们最多让对方显示错误的在线状态或投递状态，属于已接受的风险。

字节预算（估算）：普通聊天事件约 231 字节，一包放 4 条；900 字节文本的事件也放得下；阈值 3 的叠层事件约 283 字节，阈值 10 约 591 字节；32 人的 Have 约 680 字节，放不下时分多帧。

### 6.3 局域网

- 一个 UDP socket，默认端口 47480（不与 lolPing 的 47474 冲突）；多房间靠包头 `room_id` 区分。
- Have 向 `255.255.255.255` 和各网卡定向广播地址发送；其他帧单播到对方最近的来源地址。
- 收到包时，先做洪水防护，再解密：每个来源 IP 100 包/秒，总计 800 包/秒，最多跟踪 1024 个地址。
- 休眠唤醒或网络变化后重新绑定 socket。
- Windows 防火墙可能在「公用网络」下拦截入站 UDP，此时退回中继，并在 UI 提示。

### 6.4 中继

- 每个包对应一条 Nostr 临时事件（kind 在 20000–29999 内）。kind 固定为 24810（不与 lolPing 的 24747 相同；2026-11-02 实测中，收到事件的中继里只有个别按 kind 拒收）。标签 `x` 为 `room_id` 的十六进制，`content` 为包的 Base64（不超过 1600 字节）。
- Nostr 事件用**每个房间、每次运行各生成一把的密钥**签名，绝不用身份密钥，否则中继能跨房关联同一个人。
- 每个包发给所有健康的中继，收到后按 Nostr 事件 ID 去重，再按 `event_id` 去重。
- 中继列表：内置默认列表加用户配置。默认列表只收在中国大陆不开代理时直连通过实测的中继（标准见需求 4.1「国内直连」）。以后改默认列表时至少保留 3 个旧中继，否则新旧版本互相找不到。
- 默认列表（2026-11-02 定，只在四川电信的 3 个网络上实测）：`wss://relay.nostrfeed.com`、`wss://relay.ditto.pub`、`wss://purplerelay.com`、`wss://relay.mostro.network`、`wss://relay.wisp.talk`、`wss://data-space.world/r/relais-public-2`、`wss://relay.dreamith.to`、`wss://relay.gulugulu.moe`。2026-11-03 M1-4 跨网验收时，用移动或联通手机热点、关闭代理直连，能经默认中继完成联机；逐个中继在该网络上的测试结果待记录。
- 健康判断沿用 lolPing：25 秒收不到自己事件的回显就重连（退避 2 秒到 60 秒）；`rate-limited` 冷却 30 秒；`blocked`、`restricted`、`auth-required`、`pow`、`invalid` 则本次运行不再使用该中继。
- **显式约束**：临时事件没有存储保证，不能当历史数据库，也不能指望它转交给离线成员。

### 6.5 路径选择

每个 Have 都带发送方在这条路径上的周期 `period_s`（后台房比活跃房慢，接收方无从得知对方的房间是否活跃）。超过该周期的 3 倍没收到对方的包，就认为这条路径断开。

- `Lan`：局域网路径未断开（对方活跃时约 15 秒）。
- `Relay`：中继路径未断开（对方活跃时约 90 秒）。
- `Unknown`：都断开，UI 视为离线。

发送时，局域网在线成员走 UDP。只要存在非局域网的在线成员，或局域网上一个在线成员都没有，就再发一份到中继。关闭「允许互联网」后只走局域网，不连接任何中继。

### 6.6 中继预算

单客户端发送上限 5 条/秒、突发 10 条（lolPing 实测通过的强度）。发送队列优先级：本人实时事件 > Have > 补齐响应。接收上限 200 条/秒。

| 场景（32 人房，估算） | 原设计（逐成员 ACK） | 现设计 |
|------------------------|----------------------|--------|
| 一次叠层（3 条聊天 + 1 个叠层事件） | 128 次发布，中继转发约 4000 次 | 4 次发布 + 约 1–2 个 Have |
| 周期心跳 | — | 全房约 1 条/秒 |
| 经中继补齐 500 条聊天 | — | 125 包，3 包/秒，约 42 秒 |
| 经中继补齐 5000 条聊天 | 逐条约 17 分钟 | 1250 包，约 7 分钟，因此默认不走中继 |

**实现状态（M1-4，6.4–6.6）**：已按上述规则实现。中继连接用 WebSocket + 系统证书（Windows SChannel），和浏览器一样能通过会检查加密流量的杀毒软件或公司代理。收到的中继事件只看 kind 和 `x` 标签，不验 Nostr 层签名：包本身已用房间密钥认证加密，中继也会验签。中继 Have 每 30 秒；经中继回应 Want 每秒 3 包。「允许互联网」开关和中继列表存在本机设置里（默认开启、默认 8 个中继），改了之后整个连接池重建；设置页界面在 M1-5。界面在成员旁显示「局域网 / 中继 / 离线」，房间标题旁显示中继连接数。2026-11-03 跨网两机验收通过（release 版 exe，一台家里宽带、一台移动或联通手机热点，都关闭代理）：进房、实时聊天、连发叠层两边层数一致、成员显示「中继」、关掉重开后数据还在。

### 6.7 防灌水

包大小上限、上述速率限制、状态事件序号上限、每次 Want 最多 64 个事件。持码者仍可灌聊天，这只影响聊天窗口，不影响层数和房间状态。

## 7. 送达与同步

只有一套机制：**尽力广播 + 按作者序号补齐**。不做逐成员 ACK，没有独立的 outbox 表（「待确认」就是 `events` 中作者为本人、`delivery = Pending` 的行）。

### 7.1 发送与确认

1. 事件写入 `events`，`delivery = Pending`。
2. 广播一次；未确认时在 6、15、30 秒后重发（第一次重发晚于 Have 的最长延迟 5 秒，避免确认还在路上就重发），之后停止主动重发，由周期 Have 触发补齐。
3. 收到任一其他成员的 Have，其中本人的序号 ≥ 该事件的 `seq`，就标记 `Sent`。这个状态只是界面提示，事件仍可被任何人继续补齐。

没有「失败」状态。事件已经在日志里，迟早会在成员相遇时送达，所以也不存在「消息失败但叠层已算」的矛盾，用户无需手动重发。

### 7.2 Have

```text
HaveEntry { author: 短 ID, state_max: u64, chat_max: u64 }   # 对每位作者，从 1 起连续持有到的最大序号（有空洞时只报到空洞之前，否则同伴会来要本机其实没有的事件）
```

发送时机：

| 时机 | 局域网 | 中继 |
|------|--------|------|
| 活跃房周期 | 5 秒 | 30 秒 |
| 后台房周期 | 30 秒 | 120 秒 |
| 收到新的实时事件后（补齐帧不触发） | 随机延迟 1–5 秒 | 同左 |
| 首次发现新成员或网络恢复 | 随机延迟 0–2 秒 | 同左 |

**抑制**：随机延迟期间如果收到别人的 Have，且我向量里的每个序号都不超过它，就取消发送。这样一条消息通常只产生一两个 Have，作者也足够得到确认；新成员上线时也不会引来所有人同时回应。周期 Have 同时带 ±20% 的抖动。

### 7.3 补齐（只拉不推）

```text
收到同伴的 Have：
  对其中每位作者：
    state 缺口 = [1, 对方 state_max] 中本地没有的序号
    chat 缺口  = [该作者的 chat_floor, 对方 chat_max] 中本地没有的序号
  有缺口就排入 Want 队列
  每个 Want 最多 64 个事件；一个未完成不发下一个；5 秒没进展换同伴
  同一缺口对同一同伴，本次运行最多问 3 次
```

- 对方没有所请求的事件时不回复，由请求方超时后换人。任何持有事件的成员都可以提供，事件带签名，不怕被篡改。
- 响应发送速率：局域网 50 包/秒，中继 3 包/秒。
- 状态缺口始终要补；聊天缺口问不到就留着，遇到新同伴再问。
- 本地默认保留全部事件，第一版不自动删除。`history_limit_*` 只决定新成员向别人要多少、以及本机最多答应给多少。

### 7.4 新成员同步（`Joining`）

1. 解析房间码，派生密钥，开始在局域网和中继发 Have（向量为空）。
2. 收到第一个同伴的 Have 后，按 7.3 拉取全部状态事件。
3. 发 `WantFloors { n }` 询问最近 n 条聊天的分界，n 取当前路径对应的本机上限（默认局域网 5000、中继 500）。对方返回每位作者的 `floor_seq`，写入 `chat_floor`；不在返回列表中的作者，`chat_floor = 对方 chat_max + 1`。聊天补齐由 7.3 的普通流程完成。
4. 验证 `RoomCreate` 匹配 `owner_tag`，且状态缺口已补齐后，转为 `Active`，发出 `Join`（如尚未加入）和 `Profile`，已读游标移到当前最大值。聊天可继续在后台补齐。

`Joining` 期间不能发言，也不生成叠层事件。无人在线就一直等待，UI 说明原因并允许取消。

### 7.5 多房间

- 活跃房按 7.2 的高频周期，后台房降频，但都保持订阅，以便接收消息和叠层。
- 已退出的房间不再有任何网络活动。
- 已解散的房间不主动发 Have；收到别人的 Have 且对方尚不知道解散时，回一次 `Dissolve` 事件（限频），让迟到的成员也能得知。

**实现状态（M1-3）**：已实现实时广播（只发一次）、周期 Have 与延迟 Have 及其抑制、按 Want 补齐**状态事件**、Joining 转 Active、已解散房间回告解散。以下留给 M2：聊天补齐（WantFloors / Floors、chat_floor）、6/15/30 秒重发、发送中/已发送、网络变化后重新绑定 socket，以及后台房降频（目前所有房间都按活跃房的 5 秒周期）。所以 M1-3 中离线期间错过的聊天不会补回，但层数、房主、规则、成员一定会补齐。M1-4 起这些同步也经中继进行，规则见 6.5、6.6。

### 7.6 历史可用性（架构声明）

持久化真相在各节点 SQLite；系统不提供云端拉取。产品文案与验收均按「对等补齐」理解。

## 8. 房间状态

### 8.1 由状态事件推导

全部是状态事件集合的纯函数，同一作者的事件按 `seq` 排序：

| 状态 | 推导规则 |
|------|----------|
| 房主 | 匹配 `owner_tag` 的作者；其 `seq` 最小的 `RoomCreate` 生效 |
| 成员 | 每位作者最后一条 `Join` / `Leave` 决定是否在房 |
| 昵称 | 每位作者 `seq` 最大的 `Profile`；没有资料时显示指纹摘要 |
| 群名 | 房主 `seq` 最大的 `RoomCreate` / `Rename` |
| 规则 | 房主事件中 epoch 严格递增的 `RoomCreate` / `ConfigNotice`；当前规则取最大 epoch |
| 解散 | 房主 `seq` 最小的 `Dissolve`，其 `ts_ms` 为 `dissolve_ts` |

- 非房主发的 `Rename`、`ConfigNotice`、`Dissolve` 入库但不生效。
- `ts_ms > dissolve_ts` 的聊天入库但不显示。
- 房主退出不等于解散；房主身份永久绑定其密钥。

### 8.2 房间状态机

```text
Joining ──同步完成──▶ Active ──leave──▶ Left ──重新输入房间码──▶ Joining
                        │
                     收到 Dissolve
                        ▼
                    Dissolved（只读，不可恢复）
```

- 只有 `Active` 可以发送事件。
- `Joining` 取消时删除该房间的本地记录。

### 8.3 恢复备份

- 身份备份和房间备份都必须设口令（Argon2id 派生密钥后加密）。
- 本机已有身份时，导入须明确确认覆盖。
- 恢复后所有房间回到 `Joining`，从同伴拿到本人的最新序号后才能发言。这样序号不会和旧事件重复。
- 只有身份备份时，用户重新输入房间码，流程相同。本人的层数由重放恢复。

## 9. 数据模型

### 9.1 表（SQLite）

| 表 | 内容 |
|----|------|
| `identity` | member_id、昵称、私钥密文 |
| `rooms` | room_id、房间码密文、owner_tag、房主、群名缓存、状态、上次活跃、免打扰、置顶 |
| `room_rules` | room_id + rule_epoch、window_ms、threshold、cooldown_ms |
| `members` | room_id + member_id、昵称缓存、是否在房、层数缓存 |
| `events` | event_id、room_id、author_id、stream、seq、ts_ms、kind、body、sig、local_seq、display_ts、delivery、is_fork |
| `sync_state` | room_id + author_id、chat_floor |
| `read_state` | room_id、已读 local_seq |
| `settings` | 本机音效、中继开关与列表、N、备份偏好等 |

`events` 需要索引：`(room_id, author_id, stream, seq)`、`(room_id, display_ts, event_id)`、`(room_id, local_seq)`。

实现状态（M1-2）：已建 `identity`、`rooms`（另含 `dissolve_ts` 缓存列）、`room_rules`、`members`、`events`（另含 `format` 列，还原事件验签要用）、`read_state`；`sync_state` 尚未建，在 M2 以新版本升级加入。表结构版本记在 `PRAGMA user_version`。M1-4 升到第 2 版，加入 `settings`（键值，值为 JSON 文本；没存过的项用默认值，所以中继列表只在用户改过后才落盘）。

路径和在线状态只放内存，不落盘。

### 9.2 缓存与权威

- `members` 和 `rooms` 里的缓存字段都能从 `events` 重建。
- 权威 = 按第 5.4 节和第 8.1 节重放已入库的状态事件。

### 9.3 敏感数据

- 私钥和房间码用本机主密钥加密（XChaCha20-Poly1305）后存入 SQLite，不明文落盘，也不进日志。本机主密钥是 32 字节随机数，存在 Windows 凭据管理器里（由 DPAPI 按当前 Windows 账户保护）。主密钥取不到或解密失败时报错，不会生成新身份覆盖旧的。
- 聊天记录第一版明文存储，不防能直接访问本机文件的人。

## 11. 部署与安全边界

### 11.1 交付

- 单一 Windows 安装包（Tauri）。
- 安装包内置心之钢音效（约 33 KB 的 mp3），随前端一起打包，界面收到实时叠层通知时直接播放，不需要放开任何文件读取权限。音效和应用图标都是第三方游戏素材，只限群友私下使用，公开发布前需要替换。
- 更新通道可预留。

### 11.2 不部署

- 自有业务服、云消息库、自营必须中继。用户可以自愿填写自己的中继地址。

### 11.3 威胁模型

| 攻击者 | 能做什么 | 不能做什么 |
|--------|----------|------------|
| 中继、网络窃听者 | 看到 IP、`room_id`、时间；丢弃、延迟或重放密文 | 读取内容；伪造事件；跨房关联同一个人的 Nostr 密钥 |
| 持有房间码的人 | 读取全部内容；进房；灌聊天；伪造 Have 等控制帧 | 冒充其他成员发言；冒充房主；改规则或解散 |
| 改过的客户端（已接受） | 伪造时间戳和触发消息来刷本人层数；用同一序号发不同内容 | 影响别人的层数 |

心之钢的目标是防止普通客户端重复计数和成员间分歧，不防作弊。没有服务器时，时间只能由作者自己提供，改过的客户端总能造出满足规则的时间戳。

## 12. 第一版之后（P1 预留）

下面只记录审查时想清楚的要点，第一版不实现。

- **打洞直连**：lolPing 没有这部分，属于全新工作量。优先评估 iroh（支持打洞和中继回退），但其文档说明公共中继只适合开发测试，生产要付费或自建，与「不自建」有冲突，届时需要决策。引入时再决定 UDP 还是 QUIC，并增加 `Direct` 路径。
- **好友系统**：好友码放完整公钥（只有指纹无法加密）；每个身份由公钥派生一个中继主题作为汇合点；增加 X25519 密钥协商；离线请求需要收件箱，否则对方不在线时会丢失。
- **私聊房**：房间密钥由双方公钥协商得出，不需要先发邀请，对方离线也能建。
- **自定义头像**：限制大小后分片传输，或走 Have 风格的按需拉取。
- **其他**：摸鱼看板；macOS/Linux；房主转让；成员能力令牌（非共享房间码）以支持真踢人；换码时迁移历史和层数；长消息分片。

## 13. 决策记录

| 决策 | 原因 |
|------|------|
| 状态事件永不裁剪，N 只限制聊天 | 层数、房主、规则都靠重放，裁剪后新成员算不对 |
| 验签后一律入库，有效性在重放时算 | 入库时按状态丢弃会让结果依赖到达顺序 |
| 叠层事件自带触发消息的 ID 和时间 | 校验不依赖聊天原文是否还在 |
| 删除 `stacks_after`、`cooldown_ms` | 作者可任意填写，且能从日志算出 |
| 只在 `send_text` 路径判定叠层 | 同步回来的本人旧消息不会重复触发 |
| `memberId` 直接用公钥 | 验签不查表，无法冒充 |
| 房间码绑定房主公钥摘要 | 所有成员共享房间密钥，必须有独立的房主信任根 |
| 去掉逐成员 ACK，合并可靠层与同步 | 群里总有人离线；32 人房一次叠层要 128 次发布；中继没有单播 |
| 去掉「失败」状态 | 事件已在日志中，迟早会送达；避免「消息失败但叠层已算」 |
| 按本机 `local_seq` 记已读 | 迟到的旧消息也要算未读 |
| 只防君子 | 无服务器时时间戳只能由作者提供 |
| 打洞和好友移出第一版 | 中继已能兜底跨网；优先验证玩法 |
| 中继列表可配置 | 公共中继的可达性未验证，需要退路 |
| 内置心之钢音效 | 所有者 2026-11-02 决定；群友私下使用，装好就能响，不用自己找文件 |
| 默认中继只认国内直连 | 多数群友不开代理；开代理才能连的中继（如 damus、nos.lol）在国内直连被封，放进默认列表会让不开代理的人连不上 |
| 第一版不用 QUIC | 没有打洞时，小包 UDP 加对等补齐已经够用 |
| 第一版头像自动生成 | 1200 字节的包放不下图片，分片传输不是玩法核心 |
| 中继默认补 500 条，局域网 5000 条 | 中继 5000 条约需 7 分钟，还会占满公共设施的额度 |
