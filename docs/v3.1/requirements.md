# lolGang 3.1.1 需求

> 状态：已定（2026-11-09），所有者同意第 6 节的建议。计划和步骤见 [plan.md](plan.md)。
> 来源：所有者 2026-11-09 提的五条（去掉 Linux、桌面图标、性能、代码重复和结构、其他问题）。
> 前提：3.0.0 已由所有者发版（标签 v3.0.0，CI 三个平台通过，Release 有 exe、dmg、app.tar.gz、AppImage、deb 和 latest.json），
> 所有者本机已自动更新到 3.0.0。

3.1.1 是小版本：不加新功能、不改通信协议、不改数据库表结构。

## 1. 去掉 Linux 支持（R1）

- 不再出 Linux 安装包（AppImage、deb），CI 和发版工作流不再在 Linux 上编译、测试、打包。
- 删掉只给 Linux 用的东西：
  - 键鼠监听 `src-tauri/src/input/linux.rs`（784 行）和 `keymap.rs` 里 X11 的部分（macOS 部分留着），依赖 `x11rb`；
  - Xvfb 里的 X11 输入测试；
  - 「有键被窗口管理器占着」的提示整套：只有 Linux 会出现（`input::set_warning`、状态里的 `inputWarning`、
    每 5 秒的 `watch_status` 和 `status://changed` 推送、信号页的提示条）；
  - 自动更新里「deb 装的不能自动更新」的分支（`update.rs` 的 `can_install`、关于页那句提示、`UpdateView.canInstall`）；
  - 三个工作流里 Linux 的系统库安装（WebKitGTK、ALSA 等）、`scripts/release.mjs` 里 linux 的产物；
  - README、关于页、代码注释里关于 Linux 的说明。
- macOS 保留，仍是实验版。别的系统上键鼠监听照旧走 `stub.rs`（启动时报不支持），但不保证能编译、不测试。
- 队伍页显示队友平台时，「Linux」这个名字留着：还装着 3.0.0 Linux 版的队友会报这个平台。
- **后果**（所有者已接受）：latest.json 里不再有 Linux，装着 3.0.0 Linux 版的人点「检查更新」会提示出错，停在 3.0.0。

## 2. 桌面图标还是旧的（R2）

**原因（已查明）**：不是安装出了错，是 Windows 的图标缓存没刷新。

- 桌面快捷方式指向 `lolgang.exe`，自己不带图标，显示的是 exe 里的图标。Windows 按路径把这个图标缓存起来；
  路径一直是 `D:\Program Files\lolGang\lolgang.exe` 没变，所以一直用缓存里的旧图。
- 任务栏右下角是程序运行时从 exe 里现读的图标，所以已经是新图；安装目录里看到的也是新图。
- Tauri 的 NSIS 安装模板装完不通知系统「图标变了」（模板里没有 `SHChangeNotify`），自动更新时还会跳过重建快捷方式，
  所以缓存不会自己失效。

**所有者现在就能做的**：在「运行」（Win+R）里执行 `ie4uinit.exe -show`（Windows 10、11 刷新图标缓存），或者注销再登录。

**3.1.1 要做**：安装（包括自动更新）结束时通知 Windows 图标变了：在 `src-tauri/windows/hooks.nsh` 的装完钩子里调
`SHChangeNotify(SHCNE_ASSOCCHANGED)`。以后再换图标，用户不用手动刷新。只通知不够的话，再在更新时重建桌面快捷方式。

## 3. 性能（R3）

逐项查过：数据库查询、内存、计算量、I/O、缓存、并发。找到的问题按影响从大到小：

| 编号 | 问题 | 证据 | 改法 |
|---|---|---|---|
| P1 | 节点每 100 毫秒、每个队伍查两次「本机持有哪些事件」，每次读出这个队伍的**全部**事件行重新算，空闲时也一样（约 20 次全表读/秒）。2.0 打对线留下的命中事件越多越慢 | `node/mod.rs` 的 `check_want`、`plan_want` 每次先调 `core.holdings`；`storage/events.rs` 的 `holdings_rows` 是 `SELECT author_id, seq FROM events WHERE room_id = ?` | 先判断有没有要做的（有没有在途的 Want、有没有队友、队伍是否解散）再查；持有情况缓存在内存里，只在写入新事件时更新 |
| P2 | 每取一张表情图（`emote://`）就新开一个系统线程；回应头 `no-store`，同一张图每次都从磁盘重读 | `lib.rs` 的 `register_asynchronous_uri_scheme_protocol` 里 `std::thread::spawn`；`Cache-Control: no-store` | 用 Tauri 的阻塞线程池（`spawn_blocking`）；静态图按自己内容的哈希命名、永远不变，给长缓存。动图和音效会随重新导入变，404 也不能缓存，这几样保持不缓存。**M3 实测**：WebView2 不缓存自定义协议的回应，长缓存头不起作用（同一个页面里同一张图本来就复用），所以没加，只改了线程池 |
| P3 | 透明窗口线程很多消息都先去主线程查一遍显示器（`refresh`），说话时的倒计时每秒一次也查；本来就有每 3 秒的轮询 | `overlay/mod.rs` 有 9 处 `self.refresh()`，包括 `speaking` | 只在要按位置放东西（开轮盘、放信号、放表情、冒字）时查；倒计时、提示这类只用主显示器的不查 |
| P4 | 历史记录每加一条都扫一遍全表：算所有语音的总大小、删多余的行 | `storage/history.rs` 的 `trim`，`history.rs` 每次 `add` 后都调 | 超过上限一定余量（比如 50 条）才修剪；语音总大小在内存里记着，启动时算一次 |
| P5 | 语音线程每 20 毫秒的混音、重采样都新分配内存；麦克风回调（声卡线程）里也分配 | `voice/mod.rs` 的 `mix`、`play`；`voice/resample.rs` 的 `process`；`voice/audio.rs` 的回调 | 复用缓冲区，声卡线程里不分配内存 |
| P6 | 聊天框取记录、取语音是同步命令：在主线程上等历史记录线程回话 | `api.rs` 的 `history_list`、`history_play` | 改成异步命令，不占主线程 |
| P7 | 每个包（在线状态每 5 秒、说话时每秒约 2.5 个语音帧）都发给全部 8 个中继，经中继说话时上行约 20 包/秒 | `transport/relay.rs` 的 `publish`：「发给所有可用中继」 | **只评估、不改**（所有者已定）：发给最好的 3 个、收照常全听能省流量和 CPU，但中继不稳时可能连不上。3.1.1 把评估结果写进发版说明，改不改以后再定。**M6 评估**：一个 400 毫秒的语音帧签成 Nostr 事件约 1.7 KB，经中继说话时每人上行约 2.5 × 8 = 20 个事件、约 34 KB/秒，听的人每个事件也从每个连着的中继各收一份；只发最好的 3 个约 13 KB/秒，上下行都省约六成。代价：发的人和听的人连着的中继不一定重合，只发 3 个时，中继不稳会丢包或连不上（现在 8 个里有一个共同的就能到）。建议以后先按回显成功率挑中继、再实测丢包，3.1.1 不改 |
| P8 | （M3 量空闲 CPU 时发现）透明窗口放音效用的 AudioContext 建好后一直在跑，没有声音也在混静音：空闲 60 秒里网页进程约 0.4 秒、系统音频服务约 0.2 秒 CPU | `src/overlay/soundBank.ts` 的 `new AudioContext`，只在播放时 `resume`，从不暂停 | 3 秒没有声音就暂停，下次放声音时再启动 |

查过、没问题的（记下来，免得以后重查）：

- **N+1 查询**：队员列表、历史记录、队伍页都是一次查询拿全；没有循环里逐条查库的地方。
- **队伍状态重放**：每收到一批事件就从全部事件重放（`rooms::apply_state`），算法是 O(n)。3.0 不再产生命中事件，事件数不再涨，先不改。
- **内存泄漏**：没找到会一直涨的。离线（没发 Bye 就掉线）的队友，在线状态会留在内存里直到重启，每人几十字节，不改。
  聊天框藏起来时还在往记录里加，下次打开会整份换掉，有上限。
- **并发模型**：每个子系统一个线程、用通道传消息，节点跑在 tokio 上。这个结构合理，持锁时不等别的线程。
  问题只有 P2（每个请求开一个线程）和 P6（主线程同步等）。
- **数据库索引**：events、history 的查询都走了索引。

## 4. 代码重复与结构（R4）

只做「不改行为」的整理，改完全部测试照旧通过。

| 编号 | 问题 | 改法 |
|---|---|---|
| D1 | 透明窗口里「第几号显示器，没有就用主显示器」写了 3 遍（`overlay/mod.rs` 的 `checked_sub(1)`） | 合成一个函数 |
| D2 | 公钥转十六进制：`overlay/mod.rs` 手写 2 处，别处用 `team::hex`；`hex` 放在 team 里也不合适（emotes、history、panel 都在用） | 挪到 `crypto`，统一用它 |
| D3 | 透明窗口和三个小窗口（队伍面板、投票、聊天框）建窗口的参数大半相同（透明、无边框、置顶、不进任务栏、同一串浏览器参数） | 共用一个建窗口的函数 |
| D4 | 说话键、面板键的合法性检查几乎一样（候选列表加「被占的键」） | 合成一个函数 |
| D5 | 前端透明窗口的 5 个文件各写一个 `div()`，聊天框又写一个 `el()` | 放进一个共享的小文件 |
| S1 | `team.rs`（718 行）一个文件干四件事：拼队伍页、队伍命令、在线状态、把节点的通知分发给各模块 | 拆成 `team/` 下几个文件，只挪代码。**放到以后**（见第 6 节第 4 条） |

| S3 | 快捷键页在前端又写了一遍撞键规则，用来解释「为什么被换了」（`ShortcutsPage.tsx` 的 `marks`），规则有两份 | Rust 的 `normalize` 直接返回「哪个键被换了、和谁撞了」，前端只管显示 |

没发现过度设计。下面这些是有意留着的旧东西，3.1.1 不动：

- 2.0.1 从「钢一下」迁移安装的 NSIS 钩子：等确认大家都更新到 3.x 以后再删（建议 3.2）；
- 2.0 的协议兼容（在线状态里的 `laning`、命中事件入库不算）：还有 2.0 的队友时要留；
- 数据库里不再读写的 `stacks`、`taken` 两列：为了不改旧库；
- `settings2` 这个名字：历史原因，改名没有收益。

## 6. 所有者的决定（2026-11-09，「按建议来」）

1. **Linux 3.0.0 的用户**：接受停在 3.0.0、点「检查更新」会提示出错。
2. **P7 少发几个中继**：只评估、不改。
3. **O1 内容安全策略**：做，每个窗口实测后再发版。
4. **S1、S2 拆文件**：当时没给建议，这里定为**放到以后**（建议 3.2 单独做）。理由：3.1.1 是小版本，
   只挪代码的大改动和其他改动混在一起不好复盘；单独做的话，那一版的 diff 只有搬家，一眼能看出没改行为。
   所有者想在这一版就做，说一声加进 M4。
5. **版本号**：3.1.1（跳过 3.1.0）。
